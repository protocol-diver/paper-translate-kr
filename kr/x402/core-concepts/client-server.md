이러한 역할을 이해하는 것은 x402 를 사용한 프로그래밍 결제 서비스를 설계, 구축 또는 통합하는 데 필수적입니다.

**참고**\
클라이언트(Client)는 HTTP 요청을 보내는 기술적 구성 요소를 의미합니다. 실제로는 보통 리소스를 구매하는 _구매자_에 해당합니다.

서버(Server)는 요청에 응답하는 기술적 구성 요소를 의미합니다. 실제로는 보통 리소스를 제공하는 _판매자_에 해당합니다.

### 클라이언트 역할

클라이언트는 유료 리소스에 접근하기 위해 요청을 시작하는 주체입니다.

클라이언트에는 다음이 포함될 수 있습니다:

* 사람이 사용하는 애플리케이션
* 자율 에이전트
* 사용자 또는 시스템을 대신하여 동작하는 프로그래밍 서비스

#### 책임

* **요청 시작:** 리소스 서버에 HTTP 요청을 전송합니다.
* **결제 요구 처리:** `402 Payment Required` 응답을 읽고 결제 정보를 추출합니다.
* **결제 페이로드 준비:** 제공된 결제 요구사항을 사용하여 유효한 결제 페이로드를 생성합니다.
* **결제 포함 재요청:** 서명된 결제 페이로드를 `PAYMENT-SIGNATURE` 헤더에 포함하여 요청을 다시 보냅니다.

클라이언트는 암호화폐 지갑 외에 계정, 자격 증명 또는 세션 토큰을 관리할 필요가 없습니다. 모든 상호작용은 상태 비저장(stateless)이며 표준 HTTP 요청을 통해 이루어집니다.

### 서버 역할

서버는 자신의 서비스에 대한 접근에 결제를 요구하는 리소스 제공자입니다.

서버에는 다음이 포함될 수 있습니다:

* API 서비스
* 콘텐츠 제공자
* 수익화가 필요한 모든 HTTP 접근 가능 리소스

#### 책임

* **결제 요구 정의:** 인증되지 않은 요청에 대해 HTTP `402 Payment Required` 로 응답하고, 응답 본문에 필요한 모든 결제 정보를 포함합니다.
* **결제 페이로드 검증:** 들어오는 결제 페이로드를 로컬에서 검증하거나 중개자(facilitator) 서비스를 사용하여 검증합니다.
* **거래 정산:** 검증이 성공하면 결제를 정산합니다.
* **리소스 제공:** 결제가 확인되면 요청된 리소스를 클라이언트에 반환합니다.

서버는 클라이언트의 신원을 관리하거나 세션 상태를 유지할 필요가 없습니다. 검증과 정산은 요청 단위로 처리됩니다.

#### Solana 에서의 중복 정산 문제

서버가 중개자를 사용하지 않고 직접 Solana 에서 결제를 정산하는 경우, 경쟁 상태(race condition)에 유의해야 합니다. 동일한 서명된 결제 트랜잭션이 온체인에서 첫 번째 제출이 확정되기 전에 여러 번 제출될 수 있습니다. Solana의 RPC는 네트워크가 합의 단계에서 중복을 제거하기 때문에 각 제출에 대해 "성공"을 반환할 수 있습니다. 악의적인 클라이언트는 이를 악용하여 한 번만 결제하고 여러 리소스에 접근할 수 있습니다.

이를 방지하기 위해, Solana 결제를 직접 정산하는 서버는 **현재 정산 중인 트랜잭션 페이로드를 위한 짧은 수명의 인메모리 캐시**를 반드시 유지해야 합니다:

1. 검증이 성공하면 트랜잭션 페이로드에서 캐시 키를 생성합니다 (예: base64로 인코딩된 트랜잭션 문자열).
2. 해당 키가 이미 캐시에 존재하면 `"duplicate_settlement"` 오류로 정산을 거부합니다.
3. 키가 존재하지 않으면 캐시에 추가하고 정산을 진행합니다.
4. 120초 이상 지난 항목은 제거합니다 (Solana 블록해시 수명의 약 2배).

중개자를 사용하는 경우, x402 SVM 라이브러리는 `SettlementCache`를 통해 중복 정산 방지를 기본적으로 제공합니다. 자세한 내용은 [Exact SVM Scheme Specification](https://github.com/x402-foundation/x402/blob/main/specs/schemes/exact/scheme_exact_svm.md)을 참고하세요.

### 통신 흐름

x402 프로토콜에서 클라이언트와 서버 간의 일반적인 흐름은 다음과 같습니다:

1. **클라이언트가 요청 시작:** 유료 리소스를 요청합니다.
2. **서버가 `402 Payment Required`로 응답:** 응답 본문에 결제 요구사항을 포함합니다.
3. **클라이언트가 결제 페이로드 생성 및 제출:** 제공된 요구사항을 기반으로 생성하고, `PAYMENT-SIGNATURE` 헤더(Base64 인코딩)에 포함합니다.
4. **서버가 결제 페이로드 검증:** 로컬 또는 중개자 서비스를 통해 검증합니다.
5. **서버가 결제 정산 및 완료 확인**
6. **서버가 리소스 응답 반환:** 성공 시 요청된 리소스, 실패 시 오류 응답을 반환하며, 두 경우 모두 `PAYMENT-RESPONSE` 헤더(Base64 인코딩)에 정산 정보를 포함합니다.

### 요약

x402 프로토콜에서:

* **클라이언트**는 리소스를 요청하고 서명된 결제 페이로드를 제공합니다.
* **서버**는 결제 요구사항을 적용하고, 거래를 검증 및 정산한 후 결제가 성공하면 리소스를 제공합니다.

이 상호작용은 상태 비저장(stateless), HTTP 기반이며, 인간이 사용하는 애플리케이션과 자동화된 에이전트 모두와 호환됩니다.
